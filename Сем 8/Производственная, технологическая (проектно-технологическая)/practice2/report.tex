\structuralsection{Характеристика организации (места прохождения практики)}

Местом прохождения практики являлся Университет ИТМО, а предметной средой работ выступала система дистанционного обучения, в которой размещаются интерактивные задания для студентов. Такая среда предъявляет к программным средствам одновременно методические и технические требования: интерфейс должен быть понятным для обучающихся, алгоритмическая логика -- корректной, а развёртывание -- воспроизводимым в изолированной контейнерной инфраструктуре.

Практическая работа выполнялась в контексте разработки учебного веб-приложения, предназначенного для закрепления темы эйлеровых циклов и алгоритма Флёри. Целевой аудиторией тренажёра являются студенты, изучающие дискретную математику и теорию графов, а также преподаватели, которым необходим инструмент для выдачи самостоятельных заданий, автоматизированной проверки и демонстрации корректного построения эйлерова цикла.

Особенностью места прохождения практики является ориентация на дистанционный формат. Это означает, что программный продукт должен одинаково поддерживать учебный сценарий, режим контролируемого тестирования, передачу результатов в внешнюю среду и запуск в стандартной инфраструктуре LMS. Подобные требования соответствуют целям производственной, технологической (проектно-технологической) практики, в рамках которой результатом работы является не только код, но и законченный цифровой артефакт, пригодный для эксплуатации в учебном процессе~\cite{markina2020,gost732}.

\structuralsection{Введение}

Производственная, технологическая (проектно-технологическая) практика направлена на получение и закрепление навыков практической профессиональной деятельности, связанных с анализом требований, проектированием, программной реализацией и документированием программных средств~\cite{markina2020}. Для ИТМО особенно актуальны разработки, которые могут быть интегрированы в цифровую образовательную среду и использоваться в дистанционном обучении.

Тема настоящей практики -- разработка интерактивного тренажёра <<Алгоритм Флёри: построение эйлерова цикла в неориентированном графе>> для системы дистанционного обучения ИТМО. Выбор темы обусловлен двумя факторами. Во-первых, алгоритм Флёри является классическим алгоритмом теории графов и используется для объяснения условий существования и построения эйлеровых циклов~\cite{wilson2010,west2001}. Во-вторых, для эффективного освоения этой темы студентам недостаточно статического текста: необходимы визуализация графа, пошаговое прохождение и проверка собственных действий.

Объектом практики является образовательное веб-приложение, предназначенное для работы с неориентированными графами. Предмет практики -- методы проектирования и реализации интерактивного тренажёра, обеспечивающего генерацию эйлеровых графов, демонстрацию алгоритма Флёри и контроль усвоения материала.

Цель работы состояла в разработке интерактивного тренажёра, который можно использовать в системе дистанционного обучения ИТМО для изучения и проверки навыков построения эйлерова цикла в неориентированном графе.

Для достижения поставленной цели были решены следующие задачи:
\begin{enumerate}
  \item проанализирована предметная область и сформулированы функциональные и нефункциональные требования к тренажёру;
  \item спроектированы структура приложения, модель данных и пользовательские сценарии;
  \item реализованы серверная и клиентская части приложения;
  \item разработан режим контролируемого тестирования с оцениванием качества решения;
  \item подготовлены материалы по развёртыванию и комплект отчётной документации в соответствии с требованиями методического пособия~\cite{markina2020,gost732}.
\end{enumerate}

В основной части отчёта подробно рассмотрено выполнение этапов 2--5 рабочего плана-графика: согласование функциональных требований, проектирование интерфейса и логики тренажёра, разработка и интеграция в LMS, тестирование и устранение ошибок. Для каждого этапа описаны не только полученные результаты, но и последовательность выполненных действий, принятые решения и выполненные доработки. В приложениях приведены материалы, подготовленные по итогам этих этапов.

\subsection{Выполнение этапа согласования требований}

Работа над проектом началась не с написания кода, а с обсуждения задачи с куратором практики. На этом этапе требовалось перевести общую тему практики в набор конкретных требований к программному средству. Обсуждение было сосредоточено на том, каким должен быть тренажёр с точки зрения учебного сценария, какие действия должен выполнять пользователь и какие результаты должны фиксироваться системой.

В ходе согласования были последовательно рассмотрены следующие вопросы:
\begin{itemize}
  \item как должен быть представлен граф на экране и какие действия пользователь должен выполнять вручную;
  \item должен ли тренажёр только демонстрировать готовое решение или также проверять действия обучающегося;
  \item какие режимы работы необходимы для учебного и контрольного использования;
  \item какие ограничения и критерии оценивания следует заложить в тестовый режим;
  \item каким образом подготовленный тренажёр будет запускаться в среде дистанционного обучения.
\end{itemize}

Первоначально задача могла быть сведена к обычной визуализации алгоритма Флёри, однако после обсуждения стало ясно, что этого недостаточно для целей практики. Было решено, что система должна поддерживать не один, а несколько сценариев использования: самостоятельное построение и редактирование графа, пошаговую демонстрацию алгоритма, автоматическое выполнение и отдельный режим контролируемого тестирования. Такое уточнение повлияло на все последующие этапы: уже на стадии проектирования потребовалось учитывать как обучающую, так и оценочную функции тренажёра.

Отдельным результатом этапа стало уточнение состава проверяемых действий пользователя. В тестовом режиме необходимо было оценивать не только факт построения эйлерова цикла, но и корректность выбора рёбер в соответствии с правилом Флёри. Это решение усложнило постановку задачи, поскольку потребовало реализовать анализ пользовательского ответа на уровне отдельных шагов, а не только на уровне конечного маршрута.

\subsection{Теоретическая основа и конкретизация постановки задачи}

После согласования общих требований была уточнена математическая основа тренажёра. Эйлеровым циклом называется замкнутый маршрут в графе, проходящий по каждому ребру ровно один раз. Для существования эйлерова цикла в неориентированном графе необходимо, чтобы граф был связным по вершинам ненулевой степени и степени всех его вершин были чётными~\cite{bondy2008,harary1969}. В отчёте это условие записывается следующим образом:

\begin{equation}
\forall v \in V \quad \deg(v) \equiv 0 \pmod{2},
\label{eq:euler}
\end{equation}
где $V$ -- множество вершин графа, $\deg(v)$ -- степень вершины $v$.

Далее была проанализирована специфика самого алгоритма Флёри. Он строит эйлеров цикл поэтапно: на каждом шаге из текущей вершины выбирается ребро, которое не является мостом в остаточном графе, если существует альтернативный выбор~\cite{wilson2010,west2001}. Из этого следовало, что для корректного тренажёра требуется не только вычислять очередной шаг, но и объяснять пользователю, почему данный шаг допустим или вынужден.

По итогам этапа 2 задача была сформулирована в рабочем виде как разработка веб-приложения для системы дистанционного обучения ИТМО, которое:
\begin{itemize}
  \item визуализирует неориентированный граф и ход алгоритма;
  \item позволяет пользователю самостоятельно задавать или генерировать эйлеров граф;
  \item поддерживает пошаговое и автоматическое выполнение алгоритма Флёри;
  \item содержит отдельный режим тестирования с автоматической оценкой ответа;
  \item может быть воспроизводимо запущено в стандартной среде LMS.
\end{itemize}

Именно в таком виде постановка задачи была передана на следующий этап, где требовалось уже не обсуждать требования, а проектировать конкретную структуру интерфейса и внутренней логики системы.

Проектирование начиналось с выделения основных сценариев использования: редактирование графа, пошаговое прохождение алгоритма, автоматическая демонстрация и контролируемое тестирование.

В результате была выбрана двухпанельная композиция: слева размещается рабочая область с графом и результатами, справа -- элементы управления, настройки и блок тестирования.

\subsection{Проектирование архитектуры и логики взаимодействия}

После фиксации пользовательских сценариев был выполнен переход к проектированию внутренней структуры системы. На этом шаге нужно было определить, какие части логики следует реализовать на сервере, какие -- в браузере, и как организовать обмен данными между ними. Ключевым решением стало разделение системы на клиентский уровень, серверное Flask-приложение и отдельный алгоритмический слой. Такое разделение позволило не смешивать визуализацию с вычислительной логикой и обеспечило повторное использование алгоритмических функций в разных режимах работы.

В процессе проектирования были выделены следующие основные сущности серверной части:
\begin{itemize}
  \item модель графа, включающая список вершин и рёбер, операции модификации и базовые методы анализа;
  \item модуль реализации алгоритма Флёри, отвечающий за инициализацию, пошаговое выполнение и формирование текущего состояния;
  \item функции анализа пользовательского решения, проверяющие корректность пути и соответствие правилу Флёри;
  \item слой HTTP-маршрутов, предоставляющий интерфейс для клиентского приложения.
\end{itemize}

Выбор такой декомпозиции был связан с практическими соображениями. Если бы логика проверки и алгоритм Флёри находились только в клиентской части, было бы труднее обеспечивать единообразие поведения в учебном и тестовом режимах. Перенос вычислительной части на сервер позволил централизовать валидацию, упростить проверку ответов и уменьшить зависимость от состояния пользовательского интерфейса. Подобная архитектура соответствует типовой практике разработки веб-приложений на Python и Flask~\cite{python3docs,flaskdocs}.

\subsection{Уточнение модели данных и сценариев работы}

Отдельной задачей этапа проектирования стало определение формата представления графа. Необходимо было выбрать такую модель данных, которая, с одной стороны, позволяла бы выполнять алгоритмическую обработку на сервере, а с другой -- без лишних преобразований передавалась бы в браузер для визуализации. По этой причине была выбрана простая структура: список идентификаторов вершин и список рёбер вида <<источник -- цель>>. Такой формат удобно сериализуется в JSON и напрямую передаётся в клиентскую часть, где используется библиотека Cytoscape.js~\cite{cytoscapejs}.

После выбора модели данных был уточнён состав сценариев работы системы.

Первый сценарий -- учебный. Пользователь самостоятельно задаёт или генерирует граф, выбирает стартовую вершину и запускает алгоритм по шагам или автоматически. На этапе проектирования для этого сценария специально были заложены журнал действий, таблица маршрута и визуальная подсветка состояния графа. Эти элементы появились не как декоративные части интерфейса, а как ответ на требование сделать процесс прохождения алгоритма объяснимым.

Второй сценарий -- контрольный. Здесь проектирование было сложнее, поскольку требовалось совместить автоматическую проверку с понятной для пользователя обратной связью. Было решено, что система будет генерировать граф, принимать ответы по каждой стартовой вершине и после проверки возвращать не только итоговый балл, но и частные показатели качества решения: число корректно использованных рёбер, число замкнутых циклов и число нарушений правила Флёри. Наличие двух сценариев было зафиксировано как обязательное проектное решение, поскольку именно оно делало тренажёр одновременно учебным и контрольным инструментом.

\section{Разработка тренажёра и интеграция с LMS}

\subsection{Последовательность реализации серверной части}

Этап разработки был начат с серверной части, поскольку именно здесь сосредоточена алгоритмическая логика, определяющая корректность всего тренажёра. Реализация велась поэтапно: сначала были созданы базовые операции над графом, затем проверка условий эйлеровости, после этого -- механизм пошагового выполнения алгоритма, и только затем поверх этих сущностей был организован слой HTTP-маршрутов.

Серверная часть реализована на языке Python с использованием микрофреймворка Flask~\cite{python3docs,flaskdocs}. В модуле \texttt{app.py} инициализируется приложение, настраиваются режимы работы и описываются HTTP-маршруты. Выбор Flask был обусловлен необходимостью быстро построить компактное веб-приложение с явным разделением маршрутов, входных данных и режимов работы. Переменная окружения \texttt{APP\_MODE} определяет, запускается ли приложение в режиме обучения или тестирования, а дополнительные параметры задают число попыток, максимальный балл, временной лимит и диапазон размера графа.

Алгоритмическая логика вынесена в модуль \texttt{algorithm.py}. Ключевым элементом является класс \texttt{Graph}, в котором реализованы методы добавления и удаления вершин и рёбер, вычисления степени вершины, проверки достижимости и клонирования графа. Отдельная функция \texttt{check\_eulerian\_graph} проверяет выполнение условий эйлеровости, сформулированных в~\eqref{eq:euler}, а также связность графа по вершинам ненулевой степени. Такой порядок разработки позволил сначала получить устойчивое ядро для операций над графом, а затем строить поверх него прикладную логику тренажёра.

После этого был реализован класс \texttt{FleuryAlgorithm}, инкапсулирующий состояние пошагового выполнения. Он хранит исходный граф, его рабочую копию, стартовую вершину, построенный путь и список уже использованных рёбер. Основная трудность на данном шаге заключалась в том, чтобы корректно различать вынужденные переходы и случаи, когда пользователь должен избегать выбора моста. Для решения этой задачи была реализована отдельная проверка мостов в остаточном графе, а состояние шага было расширено служебной информацией, необходимой для последующей визуализации и объяснения выбора ребра пользователю.

Заметным элементом этапа реализации стала функция генерации случайного эйлерова графа. Изначально рассматривался вариант случайного добавления рёбер, однако он приводил к большому числу некорректных или слишком простых графов. Поэтому был выбран более устойчивый подход: сначала строится простой цикл по всем вершинам, а затем случайным образом <<переключаются>> дополнительные циклы. Такая операция сохраняет чётность степеней вершин и при дополнительной проверке позволяет получать более разнообразные, но корректные эйлеровы графы.

\subsection{Разработка клиентской части}

После стабилизации серверной логики началась реализация клиентской части. Работа над интерфейсом велась итеративно: сначала был собран минимальный рабочий экран, после чего по результатам внутренней проверки уточнялись расположение элементов, состав кнопок управления и способ отображения промежуточных состояний алгоритма.

Клиентская часть состоит из HTML-шаблона, CSS-стилей и нескольких JavaScript-модулей. Разметка страницы задаёт двухпанельную структуру: слева располагается область графа, журнал и таблица текущего маршрута, справа -- редактор графа, элементы управления алгоритмом, блок тестирования, легенда и описание. Такая структура появилась как прямое продолжение этапа проектирования: она позволила сохранить на одном экране и область визуализации, и управляющие элементы, и результаты работы алгоритма.

Визуализация графа выполняется библиотекой Cytoscape.js~\cite{cytoscapejs}. Для вершин и рёбер были последовательно настроены стили, отражающие их текущее состояние: стартовая вершина, текущая вершина, вершины маршрута, уже пройденные рёбра, мосты и повторно использованные рёбра. Это решение было принципиальным для учебного режима, поскольку позволяло превратить сухой вычислительный результат в наглядную пошаговую демонстрацию.

Для снижения связности клиентский код был разделён на модули. Модуль \texttt{training.js} отвечает за работу элементов редактора графа и учебного режима: через него обрабатываются добавление и удаление вершин и рёбер, очистка графа, генерация случайного примера и запуск алгоритма. Модуль \texttt{algorithm.js} реализует взаимодействие с сервером для инициализации, выполнения шага и автоматического прохождения алгоритма, а также обновляет журнал и таблицу маршрута. Модуль \texttt{testing.js} отвечает за сценарий контролируемого тестирования и формирует поля ввода для ответов по каждой стартовой вершине. Такое разделение облегчило последовательную доработку отдельных сценариев без переписывания всего интерфейса.

\subsection{Разработка механизма оценивания и подготовка к интеграции}

В рамках этапа разработки отдельно была реализована система оценивания тестового режима. Итоговая относительная оценка попытки вычисляется по формуле

\begin{equation}
R = 0{,}60 \cdot r_{\text{cov}} + 0{,}15 \cdot r_{\text{cycle}} + 0{,}25 \cdot r_{\text{fleury}},
\label{eq:score}
\end{equation}
где $r_{\text{cov}}$ -- доля корректно использованных рёбер, $r_{\text{cycle}}$ -- доля правильно замкнутых циклов, $r_{\text{fleury}}$ -- доля шагов, удовлетворяющих правилу Флёри.

Весовые коэффициенты в формуле~\eqref{eq:score} были подобраны в соответствии с согласованными критериями оценивания. Наибольший вклад в итоговую оценку даёт корректное прохождение по всем рёбрам, поскольку именно это отражает достижение основной учебной цели. Отдельно учитываются факт замыкания цикла и соблюдение правила выбора немостового ребра. После вычисления относительной оценки она преобразуется в дискретный балл, используемый системой дистанционного обучения.

Параллельно с реализацией логики оценивания велась подготовка приложения к интеграции в LMS. Для обеспечения воспроизводимости запуска были подготовлены файлы \texttt{Dockerfile}, \texttt{dev.yml}, \texttt{docker-compose.yml} и \texttt{spec.yml}. Конфигурация локальной разработки публикует сервис на порт \texttt{3000} и включает режим отладки, тогда как production-конфигурация задаёт параметры контейнера, лимиты ресурсов, сетевое окружение и набор переменных окружения для LMS~\cite{dockerdocs}. Это позволило завершить этап разработки не только рабочим кодом, но и подготовленной схемой запуска в учебной инфраструктуре.

\subsection{Выявленные проблемы и выполненные исправления}

Тестирование проводилось итеративно. После каждого найденного недостатка выполнялось исправление, затем соответствующий сценарий запускался повторно, а смежные функции дополнительно проверялись на отсутствие регрессий. Такой подход оказался особенно важным для случаев, в которых клиентская и серверная части влияют друг на друга.

По результатам тестирования были выполнены следующие группы исправлений:
\begin{itemize}
  \item усилена валидация входных данных, чтобы алгоритм не запускался для пустых, неэйлеровых и некорректно заданных графов;
  \item уточнено обновление клиентского состояния после каждого шага алгоритма, чтобы журнал, таблица маршрута и визуальное состояние графа оставались согласованными;
  \item доработана логика выбора рёбер в пошаговом режиме, чтобы вынужденные переходы и мосты корректно определялись и отражались в интерфейсе;
  \item проверены ограничения тестового режима по времени, числу попыток и формату ответов пользователя;
  \item подтверждена воспроизводимость контейнерного запуска без ручного изменения исходного кода и конфигурации.
\end{itemize}

После внесения исправлений подготовленные сценарии были выполнены повторно. Повторная проверка показала, что ключевые пользовательские сценарии работают стабильно, а граничные случаи обрабатываются явно, без скрытых ошибок и неоднозначных состояний интерфейса. Тем самым этап 5 завершился не только фиксацией качества результата, но и реальным циклом поиска, анализа и устранения обнаруженных проблем.

\structuralsection{Заключение}

В ходе производственной, технологической (проектно-технологической) практики была выполнена разработка интерактивного тренажёра <<Алгоритм Флёри: построение эйлерова цикла в неориентированном графе>> для системы дистанционного обучения ИТМО.

В ходе этапа согласования требований были уточнены учебные и технические ожидания к тренажёру, определены ключевые сценарии использования и зафиксированы критерии оценивания ответов пользователя. На этапе проектирования были разработаны структура интерфейса, архитектура взаимодействия клиентской, серверной и алгоритмической частей, а также модель представления графа и пользовательских действий. На этапе разработки были последовательно реализованы серверная логика, клиентский интерфейс, система оценивания и контейнерная конфигурация для интеграции в LMS. На этапе тестирования был сформирован набор сценариев проверки, выявлены проблемные случаи и выполнены исправления, обеспечившие устойчивую работу системы.

Практический результат работы представляет собой самодостаточное учебное веб-приложение, пригодное для демонстрации алгоритма Флёри, самостоятельной тренировки и текущего контроля знаний. После завершения технических этапов были также подготовлены отчётные материалы в соответствии с требованиями методического пособия. Поставленная цель достигнута, задачи практики выполнены в полном объёме.

Ниже приведён сокращённый фрагмент функции генерации случайного эйлерова графа, отражающий принцип сохранения чётности степеней вершин.

\begin{lstlisting}[language=Python, caption={Фрагмент функции генерации эйлерова графа}]
def generate_eulerian_graph(min_nodes=6, max_nodes=9):
    node_count = random.randint(min_nodes, max_nodes)
    nodes = [chr(ord('A') + i) for i in range(node_count)]

    edge_keys = set()
    for i in range(node_count):
        source = nodes[i]
        target = nodes[(i + 1) % node_count]
        edge_keys.add(Graph.edge_key(source, target))

    target_ops = random.randint(max(2, node_count // 2), max(4, node_count * 2))
    attempts_left = target_ops * 8

    while target_ops > 0 and attempts_left > 0:
        attempts_left -= 1
        cycle_len = random.randint(3, node_count)
        cycle_nodes = random.sample(nodes, cycle_len)
        cycle_edges = [
            Graph.edge_key(cycle_nodes[i], cycle_nodes[(i + 1) % cycle_len])
            for i in range(cycle_len)
        ]
\end{lstlisting}

Следующий фрагмент отражает центральную часть реализации алгоритма Флёри: на каждом шаге из текущей вершины выбирается допустимое ребро, причём при наличии альтернативы предпочтение отдаётся ребру, не являющемуся мостом в остаточном графе.

\begin{lstlisting}[language=Python, caption={Фрагмент пошагового выполнения алгоритма Флёри}]
def step(self) -> Dict:
    if self.finished:
        return self.get_state()

    neighbors = self.graph.get_neighbors(self.current_node)

    if not neighbors:
        self.finished = True
        if self.graph.edge_count() == 0 and len(self.path) > 1 and self.path[0] == self.path[-1]:
            self.valid = True
            self.message = 'Эйлеров цикл построен.'
        else:
            self.valid = False
            self.message = 'Цикл не построен: закончились доступные ребра.'
        return self.get_state()

    non_bridge_neighbors = [
        neighbor for neighbor in neighbors
        if not self._is_bridge(self.current_node, neighbor)
    ]

    forced = len(neighbors) == 1 or len(non_bridge_neighbors) == 0
    next_node = sorted(neighbors)[0] if forced else sorted(non_bridge_neighbors)[0]
    is_bridge = self._is_bridge(self.current_node, next_node)

    self.graph.remove_edge(self.current_node, next_node)
\end{lstlisting}

Следующий фрагмент иллюстрирует вычисление качества пользовательского решения в тестовом режиме.

\begin{lstlisting}[language=Python, caption={Фрагмент вычисления оценки решения}]
SCORE_WEIGHTS = {
    'edge_coverage': 0.60,
    'cycle_complete': 0.15,
    'fleury_rule': 0.25,
}

def _calculate_attempt_score(cycle_summary):
    coverage_ratio = cycle_summary.get('coverage_ratio', 0.0)
    complete_ratio = cycle_summary.get('complete_ratio', 0.0)
    fleury_ratio = cycle_summary.get('fleury_ratio', 0.0)

    weighted_ratio = (
        coverage_ratio * SCORE_WEIGHTS['edge_coverage']
        + complete_ratio * SCORE_WEIGHTS['cycle_complete']
        + fleury_ratio * SCORE_WEIGHTS['fleury_rule']
    )

    attempt_score = int(TEST_TOTAL_SCORE * weighted_ratio)
    return max(0, attempt_score)
\end{lstlisting}
